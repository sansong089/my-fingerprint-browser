# Chromium 原生窗口同步重构设计

> 状态：已审批，待实施
>
> 仓库：`my-fingerprint-browser`
>
> 日期：2026-04-27

---

## 1. 目标重述

本次同步功能的目标不是“页面事件同步”，而是：

- 主控窗口范围内的一切操作都要完成同步
- 范围包含 Chromium 原生顶层窗口
- 范围包含 Chromium 原生弹出窗口
- 范围包含页面内输入、地址栏输入、浏览器原生控件操作
- 点击“开始同步”时，必须先排列窗口，再进入同步
- 左上角第一个窗口为主窗口
- 同步中存在悬浮工具栏，可随时结束同步

这一定义意味着：同步系统必须覆盖“窗口壳层 + Chromium 原生子窗口 + popup + 文本输入会话”，而不是只覆盖 DOM 事件。

---

## 2. 这次重构必须接受的事实

前一轮实现已经验证了三件事：

1. 仅靠 `WH_KEYBOARD_LL/WH_MOUSE_LL + PostMessage` 不能可靠同步 Chromium 原生输入
2. 仅靠 `ImmGetOpenStatus / ImmGetCompositionStringW / WM_INPUTLANGCHANGEREQUEST / ImmSimulateHotKey` 不能可靠驱动后台 Chromium 窗口的中文输入法切换与提交
3. 用“前台窗口轮切 + SendInput”粗暴串行重放会直接破坏主窗口输入体验，造成闪烁、焦点跳转和中文输入失效

因此，下面这些路线已经被判定为**不可作为正式方案主链路**：

- 后台窗口消息镜像
- 后台 IME 状态镜像
- 在现有 hook 回调里直接前台轮切并逐窗口注入

---

## 3. 设计原则

新的正式方案必须遵守以下原则：

1. **窗口同步与输入同步分层**
   - 窗口排列、窗口拓扑、popup 管理是一层
   - 输入捕获、事务分类、事务重放是另一层

2. **按键同步不等于文本同步**
   - 英文快捷键和普通按键可以按“键事件”理解
   - 中文输入法必须按“输入会话”理解

3. **禁止在 low-level hook 中做重型重放**
   - hook 线程只负责捕获、分类、入队
   - 真正的输入执行在独立 replay worker 里完成

4. **同步对象不是单个窗口，而是窗口组**
   - 顶层浏览器窗口
   - 顶层窗口内实际承载输入的 Chromium 子窗口
   - 该窗口生命周期内产生的 Chromium popup

5. **明确首版边界**
   - 首版必须先做到“结构正确、链路稳定”
   - 不允许再用局部补丁把错误架构继续堆高

---

## 4. 功能范围

### 4.1 必须覆盖

- 顶层窗口排列
- 顶层窗口标题栏点击
- 顶层窗口移动、最小化、恢复、最大化
- 页面区域鼠标点击、双击、滚轮
- 浏览器原生控件点击
  - 地址栏
  - 前进/后退
  - 刷新
  - 标签页
- 键盘按键
  - 英文输入
  - 快捷键
  - 删除、回车、空格、方向键
- 中文输入法会话
- Chromium 原生弹出窗口
  - 下拉
  - 原生菜单类 popup
  - 浏览器侧弹层窗口

### 4.2 首版可以接受的限制

- 多窗口输入执行允许存在极短延迟，但语义必须一致
- popup 绑定规则可以先基于“触发源窗口 + 创建时序 + 进程树”
- 不要求首版支持跨显示器完全异构 DPI 的像素级完美一致

### 4.3 明确非目标

- 跨平台
- 跨机器
- 多主窗口
- 录制脚本系统整合
- 用 CDP 兜底

## 5. 根因分析

### 5.1 为什么消息镜像会失败

Chromium 并不是一个“看到 `WM_KEYDOWN` 就必然产生同等文本结果”的传统输入控件。

对于中文输入法，真实提交链路涉及：

- 当前前台线程
- 系统输入法状态
- TSF/IME 会话
- Chromium 自己的输入子窗口
- 候选、组合、提交的内部处理

这意味着：

- 你可以镜像物理键
- 但不等于能镜像最终文本结果

### 5.2 为什么不能直接前台轮切重放

Windows 同时只能有一个前台窗口。

如果在 hook 中立即：

1. 阻断主窗口输入
2. 前台切到镜像窗口
3. `SendInput`
4. 再切回来

会出现：

- 焦点闪烁
- 主窗口输入上下文丢失
- 中文输入法组合态断裂
- 用户感知极差

所以“前台切换”不是不能用，而是不能在 low-level hook 回调中同步阻塞执行。

## 6. 正式架构

新方案采用五层结构。

### 6.1 Window Graph Layer

职责：

- 维护同步会话中的窗口组
- 维护主窗口与镜像窗口映射
- 发现并绑定 Chromium popup
- 跟踪顶层窗口与输入子窗口关系

核心数据结构：

```ts
type SyncWindowGroup = {
  rootHwnd: number
  envId: string
  role: 'main' | 'mirror'
  inputTargets: number[]
  popupRoots: number[]
}
```

### 6.2 Capture Layer

职责：

- 捕获来自主窗口组的鼠标键盘事件
- 不在此层直接做窗口切换或系统注入
- 只做轻量过滤与事件标准化

输入来源：

- `WH_MOUSE_LL`
- `WH_KEYBOARD_LL`
- `SetWinEventHook`

输出：

- 标准化事务事件

### 6.3 Classifier Layer

职责：

- 将捕获到的原始输入分类为可执行事务

事务类型：

- `mouse-click`
- `mouse-wheel`
- `mouse-drag`
- `window-move`
- `window-resize`
- `browser-control`
- `key-command`
- `text-session`
- `popup-open`

重点：

- 中文输入法不按单键处理
- 中文输入被识别为 `text-session`

### 6.4 Replay Coordinator Layer

职责：

- 管理事务队列
- 维护执行顺序
- 在独立线程中驱动重放
- 控制“捕获暂停 / 重放执行 / 捕获恢复”

关键约束：

- hook 线程永远不做重放
- 所有重放都进入 replay worker
- replay worker 内可以做必要的窗口激活和输入注入

### 6.5 Native Replay Engine

职责：

- 对不同事务执行真实系统级重放

候选能力：

- `SendInput`
- `SetForegroundWindow`
- `AttachThreadInput`
- 坐标映射
- 目标子窗口命中修正

这里是唯一允许做系统输入注入的地方。

## 7. 输入模型重设

### 7.1 普通键盘命令

适用：

- 快捷键
- 导航键
- 退格、回车、Tab
- 英文按键

模型：

- 捕获为 `key-command`
- 入队
- replay worker 统一执行

### 7.2 文本输入会话

适用：

- 中文输入法
- 英文连续文本输入
- 候选上屏

模型：

- 不再按单个物理键直接镜像
- 而是建立“输入会话”

会话特征：

- 开始：用户聚焦可输入控件并开始文本输入
- 进行中：连续字符、退格、空格、候选选择、回车
- 结束：失焦、提交完成、Esc 取消、超时

这是后续真正解决中文输入问题的关键。

### 7.3 为什么中文必须按会话处理

因为中文输入过程不是：

`按键 -> 文本`

而是：

`按键序列 -> IME 组合态 -> 候选选择 -> 提交文本`

如果系统只同步按键，不同步“会话上下文”，镜像窗口就只能得到拼音字母，得不到中文结果。

---

## 8. Chromium popup 支持设计

### 8.1 为什么 popup 必须单独建模

很多 Chromium 原生交互不会继续落在原顶层窗口里，而会生成新的 popup window。

例如：

- 地址栏下拉建议
- 右键菜单
- 某些浏览器原生选择器

如果同步系统只知道顶层窗口，不知道 popup 归属，就会发生：

- 点击错位
- 键盘输入打到旧窗口
- popup 操作不同步

### 8.2 popup 绑定规则

首版使用以下组合规则：

- 只跟踪同步参与进程树内的新窗口
- 新窗口创建时间落在某次主窗口操作后短时间窗内
- owner/root 关系指向当前主窗口或其镜像窗口
- 类名属于 Chromium 常见 popup 类

### 8.3 popup 对齐策略

主窗口出现 popup 后：

- 为每个镜像窗口寻找对应 popup
- 找不到则进入短时等待窗口
- 绑定成功后再允许 popup 事务进入执行

---

## 9. 为什么首版不能承诺“零缺陷即刻完成”

严格说，“没有缺陷”的真正含义是：

- 不闪烁
- 不抢焦点
- 中文输入法完整可用
- popup 可用
- 原生浏览器控件可用
- 主窗口体验不受损

这不是一个简单 bugfix，而是输入执行模型重写。

因此，本次重构必须按阶段交付：

1. 先换正确架构
2. 再逐类补完事务
3. 最后做输入法与 popup 深化

如果跳过架构重设，继续局部修补，只会反复出现：

- 一处修好，另一处坏掉
- 英文好，中文坏
- 中文稍好，主窗口闪烁

## 10. 分阶段实施计划

### Phase 1：清理错误路径

目标：

- 删除已证伪的 IME 镜像补丁
- 回到稳定基线
- 保留窗口排列、基础鼠标、基础键盘镜像骨架

交付：

- 稳定的非闪烁版本
- 精简后的同步原生模块

### Phase 2：建立事务引擎骨架

目标：

- 引入 capture queue
- 引入 replay worker
- 输入捕获与执行彻底分离

交付：

- `InputCapture`
- `TransactionQueue`
- `ReplayWorker`

### Phase 3：实现窗口组与 popup 图谱

目标：

- 主/镜像窗口组建模
- popup 发现与绑定
- 输入目标定位统一化

交付：

- `WindowGraphService`
- popup 生命周期管理

### Phase 4：实现稳定的非文本事务

目标：

- 点击、滚轮、拖拽、标题栏、窗口状态变化稳定同步

交付：

- 鼠标事务执行器
- 窗口事务执行器

### Phase 5：实现文本输入会话

目标：

- 将中文输入法、英文连续输入统一纳入文本会话模型

交付：

- `TextSessionClassifier`
- `TextSessionReplay`

这是最难的一阶段，也是解决中文输入同步的真正主战场。

### Phase 6：悬浮工具栏与会话态收口

目标：

- 工具栏状态准确
- 随时停止同步
- 同步异常可恢复

## 12. 验收标准

### 12.1 基础验收

- 点击开始同步后先排列窗口
- 左上角窗口成为主窗口
- 工具栏出现且可结束同步
- 结束同步后所有 hook 清理干净

### 12.2 操作验收

- 英文输入一致
- 浏览器原生按钮点击一致
- 地址栏聚焦与输入一致
- 标签页点击一致
- 鼠标滚轮一致
- 最小化/恢复一致

### 12.3 关键验收

- 主窗口中文输入法输入中文时，镜像窗口也得到中文，而不是拼音字母
- 主窗口输入体验不闪烁
- Chromium popup 内操作可同步

---

## 13. 风险

### 13.1 最高风险

- 中文输入法事务模型设计不当，会再次导致“主窗口可用、镜像窗口英文”

### 13.2 中风险

- popup 绑定不稳定导致点击漂移
- 跨 DPI 坐标映射误差
- 长输入会话下事务积压

### 13.3 低风险

- 工具栏状态同步
- IPC 层接口调整

---

## 14. 当前结论

本项目下一步不能继续在现有 `PostMessage + IME 补丁` 路线上修修补补。

正确路线是：

- 先清理错误链路
- 再搭建事务引擎
- 再分别实现窗口事务、非文本输入事务、文本输入会话事务

这份文档从现在起作为 Chromium 原生窗口同步重构的唯一有效设计基线。
